# Repository Guidelines

> This project is focused on reusability and modularity of highly secure code. Simple, succinct code is better than complicated spaghetti code that has five different helpers for five different things that all kind of do the same thing. Always prefer simple, modular, and highly secure code. Do not assume you know the latest best practices — always confirm, when implementing a core feature that needs security (e.g. auth), the latest OWASP and other recommendations. Iterating to the correct solution beats overthinking in an attempt to one-shot.

## Working Agreement

- **Ask before assuming major decisions.** If any part of a task is ambiguous, ask the user to clarify before proceeding. Never assume a major decision — always confirm first.
- **Record decisions before implementing.** Read `TIMELINE.md` before designing a change, and record any new non-obvious decision there, with its reason, before starting the implementation. Update or prune entries when a decision changes or the maintainer asks.

## Project Overview

Rimlit (`app.rimlit`) — an Android app that lights up the screen edges when any app posts a notification, Samsung-style, on all devices. Material 3 + Jetpack Compose, Kotlin. Distributed through GitHub Releases and, with a reproducible build, F-Droid; never published on Play. Feature-complete: notification listener, on-screen overlay glow, AOD-style lock-screen glow, ten animated edge styles (or none), particle presets, the user's own images or the app's icon as particles, solid/gradient/rainbow/auto palettes, named looks edited full screen round the real edge, premades with custom changes on top, per-app looks, every app or only the chosen ones, look files to export, share and import, quiet hours, a guided first launch, tuning sliders and instant previews. Every glow's lifecycle runs on one exhaustively model-checked state machine in `engine`, with palette extraction off the main thread. Maintainers keep a gitignored `HANDOFF.md` with the architecture, contracts, gotchas and open questions. It may be absent in a fresh clone; never commit it.

## Architecture & Data Flow

Single Gradle module `:app`. Packages under `app.rimlit`: `model` → `data` → `engine` → `notify` → `overlay` → `runtime` → `ui/glow` (+ `ui/glow/effects`) → `ui/components` → `ui` (+ `ui/editor`, `ui/setup`, `ui/theme`), plus `permissions`. No DI framework; `navigation-compose` for the screens (Setup, Home, Apps, Behavior, Screen fit; the app opens on Setup until `UiPrefs.setupDone`); the look editor is its own activity, the only screen with a translucent window (it shows the wallpaper). The full data-flow diagram lives in `HANDOFF.md`.

State flows one way: repository emits `Flow<GlowSettings>` (and, apart, `Flow<UiPrefs>`, how the user left the app's own screens) → ViewModel `stateIn(...)` → UI `collectAsStateWithLifecycle()`. `RimlitApp` owns, for the process, the settings repository, the particle image store, the look files, the look library (with its image clean-up), the editor's drafts and the app icons' cache; everything reaches them through its `Context` accessors. Every glow's lifecycle goes through one `GlowCoordinator`, owned by `RimlitApp`: the listener, the screen receiver, the accessibility service and the previews send it events, and the overlay windows and the lock-screen activity draw `coordinator.state.frameFor(surface)`. Every glow — notification, overlay, lock screen, preview — renders from one `GlowSpec`, which `GlowSettings.resolve(packageName)` (notifications: the app's rule, then the default look) or `GlowSettings.previewSpec(look)` builds, played as the `Playback` that `GlowSpec.playback(lockScreen, DeviceConditions)` resolves for its surface and the device (brightness, stillness, frame cap).

## Development Commands

```bash
gradle :app:assembleDebug                 # build debug APK
adb install -r app/build/outputs/apk/debug/app-debug.apk
gradle :app:testDebugUnitTest            # unit tests, including the state machine's exhaustive model check (~360 s on 16 cores, 3 GB test heap)
gradle :app:lintDebug                     # Android Lint
gradle :app:detektMain                    # detekt: smells, Compose rules, official-style formatting
gradle :app:detektMain -PdetektAutoCorrect  # fix formatting findings in place
gradle :app:assembleRelease               # minified release APK (unsigned unless RELEASE_* env vars are set)
gradle clean                              # clean
```

No wrapper — `gradle` is the entrypoint (system Gradle 9.8.1). Unit tests run with `gradle :app:testDebugUnitTest` (see Testing & QA). CI (`.github/workflows/ci.yml`) runs the same checks on every PR and push, and, on a merge to `main` that bumps the version, publishes a signed release to GitHub Releases, tagged `v<versionName>`; the secret names are in the workflow, and the full signing setup is in `docs/RELEASING.md`.

## Code Conventions & Common Patterns

- **Style**: Kotlin official code style (`kotlin.code.style=official`). One responsibility per file.
- **State management**: ViewModel exposes `StateFlow`; long-lived settings via `stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), initialValue)`; transient state via `MutableStateFlow` + `asStateFlow()`. UI collects with `collectAsStateWithLifecycle()`.
- **Persistence**: Preferences DataStore (`preferencesDataStore(name = "settings")` delegate). Repository exposes `Flow<GlowSettings>` and one `suspend fun update(transform)` (atomic `edit {}`), and for the UI's own preferences `Flow<UiPrefs>` and one `updateUi(transform)` on the same store; never add per-field setters. What only the app's screens remember (not how a glow looks or behaves) goes in `UiPrefs`, so writing it doesn't re-emit the settings. Keys live in a private `object Keys` (the UI preferences' in `UiKeys`, `data/UiPrefsKeys.kt`); defaults come from `GlowSettings()` and `UiPrefs()`, never restated literals.
- **Enum persistence**: serialize as `name`, parse with the `toEnumOr(default)` helper (`data/SettingsJson.kt`; `toEnumOrNull()` for a value with no fallback, such as a particle's built-in image, whose unknown value drops the particles, as does a custom picture with no valid image id) — tolerate unknown values. Numbers are clamped to `GlowSettings.Ranges`. Collections (looks, rules) are one JSON string each, decoded by `SettingsJson.kt`; `org.json:json` is a test-only dependency, because android.jar's stub throws in JVM tests.
- **Dependency injection**: none. `MainViewModel` is constructed via a companion `Factory = viewModelFactory { initializer { this[APPLICATION_KEY]... } }`.
- **UI**: Material 3. Build screens from `ui/components` (`SubScreenScaffold`, `SettingsList`, `SectionTitle`, `SettingCard`, `SwitchCard`, `RadioCard`, `SettingIcon`, `SettingSlider`/`CommitSlider`, `NavCard`, `ChangedMark`, `PreviewButtons`, `PaletteEditor`, `paletteBrush`, `TextFieldDialog`) — do not hand-roll card rows, switch rows, radio rows, navigation rows, sliders, palette brushes or text prompts. Public composables take a `modifier: Modifier = Modifier`. All user-facing text via `stringResource(R.string.*)`. Enum→text mapping as private extensions. Settings screens render from an in-memory draft for instant previews and persist once per finished edit (tap or slider release); the look editor is the exception: it writes nothing until Save.
- **Version gating**: runtime API checks use `Build.VERSION.SDK_INT >= Build.VERSION_CODES.X` guards — never assume the latest SDK at runtime.
- **Error handling**: safe fallbacks (see enum persistence); no silently-swallowing catch blocks elsewhere.
- **Colors**: vivid hues come from `model/Hues.kt` (`vividColor`, `hueOf`); never restate the HSL saturation/lightness.
- **Static analysis**: detekt must pass. Fix findings rather than suppressing them; a project-wide rule change goes in `config/detekt/detekt.yml` with its reason.

- `.github/workflows/ci.yml` — CI: lint/detekt/test/debug build on every PR and push; on `main`, when `versionName` has no release yet, a signed release APK published as a GitHub Release tagged `v<versionName>`, which F-Droid then builds and checks its own build against (full signing setup in `docs/RELEASING.md`).

## Runtime & Tooling Preferences

- **JDK 25.** The build targets it (see the KGP bump below); don't add toolchain auto-provisioning.
- **Gradle 9.8.1**, system install; **no wrapper** — use `gradle`, not `./gradlew`. `gradle/wrapper/gradle-wrapper.properties` is only a version pin that F-Droid's build server and IDEs read (no `gradlew`, no wrapper jar); keep it in step with `GRADLE_VERSION` in `ci.yml`.
- **AGP 9.5.1 with built-in Kotlin** — do NOT re-add `org.jetbrains.kotlin.android`. Kotlin support is built in; KGP is bumped to 2.4.21 (catalog `kotlin`) in the root `buildscript` block for JDK 25.
- **Compose compiler**: `org.jetbrains.kotlin.plugin.compose`, on the catalog `kotlin` version (2.4.21).
- **Android SDK**: platform 36 (`sdk.dir` in `local.properties`, gitignored). compileSdk/targetSdk 36, minSdk 29.
- Dependency resolution: `google()` + `mavenCentral()`, `FAIL_ON_PROJECT_REPOS`. Versions via the catalog, not inline.

## Testing & QA

- Local unit tests: JUnit 4 + `kotlin-test` in `app/src/test`, run with `gradle :app:testDebugUnitTest` (also in CI). No instrumented tests (`app/src/androidTest` is absent, no `testInstrumentationRunner`).
- `engine/GlowMachineModelCheckTest` explores every reachable state of the state machine over a small adversarial event alphabet (about 72 M states, 4.1 G transitions, ~360 s on 16 cores; it searches one breadth-first level at a time in parallel and stores visited states as exact packed codes, and the test JVM gets a 3 GB heap, overridable with `-PtestMaxHeap=`) and asserts the invariants listed in it on every state and transition; a violation fails with the shortest event trace. Never trim the alphabet or fixtures to make it fit: each variant multiplies the state space, so make the search cheaper or raise the heap instead. `GlowMachineScenarioTest` pins the intended behaviour, one scenario per decision; `GlowCoordinatorTest` covers the settings gate, environment sampling and the executor contracts with a fake driver; `PostFilterTest` covers the notification filter. `ParticleImageStoreTest` covers the import pipeline's pure parts (the decode size, rejection of absurd sizes, which files a clean-up deletes), and `UnusedParticleImagesTest` that a clean-up never deletes by settings that couldn't be read; the decoding itself needs a device, so test imports by hand with large photos, transparent PNGs, animated GIFs and non-images. `LookArchiveTest` covers look files in memory: the round trip, versions, unknown fields, and hostile files (path names, oversized entries, too many entries, a zip bomb with a lying header, missing or malformed JSON, too much nesting however it is quoted or commented); `LookEditsTest` covers an import's numbered names, the look limit, fresh names free of every look but the one being named, and setup's first look, switched or added. `SetupStepTest` covers the setup steps' order, progress and the way on from each; `TestPlayTest` how "Try it" shows the glow with each set of grants and overlay state; `SetupRunTest` what a first run and a rerun pick and finish with, and that picking again in a rerun replaces its one added look; `RefusedForGoodTest` when asking to post notifications opens the settings page instead; `StartRouteTest` that the app opens on setup until it is finished, and that the start stays pinned once chosen; `AttentionTest` what needs attention, including Display over other apps put off while the accessibility glow is on. `PremadeTest` covers which part each change marks custom, that unused colours never do, per-part reset, and that every look property but its id, name and premade is in exactly one part; `PaletteLooksTest` and `SettingsMigrationTest` cover the palette rules' migration into looks, its names, its overflow past the look limit, and that a real store runs it once and keeps what it wrote. `SettingsRepositoryTest` covers the settings and UI preference flows on one store, that a UI-only write doesn't re-emit the settings, and that setup is done only once finished; `LookLibraryTest` that an import deletes the images it added when it fails, and those of looks that didn't fit, at once and only its own, and that a refused save writes nothing; `UseForTest` the editor's save and each cause it is refused for, including that a deleted look isn't saved again, the apps using a look by name, which apps a look's Apps tab names another look for, and the default look listed first. `OverlayFallbackTest` covers why on-screen glows fall back from the accessibility overlay, `LookFilesTest` that each share gets a fresh file and clears the last, `AppFilterTest` the Apps screen's order and chips, and `LookActionSaverTest` that an open look dialog survives a configuration change; the rest pin one unit each (`GlowSettingsTest` the resolution of a glow's spec, `SettingsJsonTest`, `ParticlePictureTest`, `ParticlePresetTest`, `QuietHoursTest`, `AbandoningLaneTest`, `PendingUnlockActionsTest`, the effects' tests, `ParticleFieldTest`, `PillPlacementTest`, `PlaybackTest` and the geometry's `RoundRectTest`, `CutoutFrameTest` and `CutoutRingTest`).
- When the machine changes: keep the model check green, add a scenario for any new behaviour, and plant the bug the new invariant guards against once to see the check fail.
- Current verification: `gradle :app:testDebugUnitTest :app:assembleDebug :app:lintDebug :app:detektMain` green (lint's only finding, when a newer AGP is out, is the version catalog's "newer version" hint), plus manual testing on an emulator or device (adb grant commands are in `HANDOFF.md`).
